# 本机内存测量与优化

2026-11-01，Windows 宿主，用户追加要求“是否会对我的内存造成压力，现在，如果是就优化”。复用原客户端、任务、记忆服务和 Hook；不关闭其他应用，不增加服务/缓存，不改变模型。代码和配置作用于 D:/ContextRail；测量在实际宿主执行。

## 当前压力与归属

首次采样可见内存 15583.4 MiB，可用2366.8 MiB（约2.31 GiB）。后续排除测量进程自身的采样可用2722 MiB（约2.66 GiB）、使用82.5%；当时页输入/页读速率均为0。两个时间点不能证明持续无压力，也不把全机可用内存波动当作本次优化收益。

后续采样 Codex 相关进程工作集合计717.9 MiB，桌面应用相关进程1999.5 MiB，原记忆监听进程29.1 MiB，其他原有进程7352.8 MiB。工作集含共享页，跨进程相加不是精确物理私有占用。当前没有活动的项目 Rail/MCP 进程；这只是当时状态，不代表打开项目连接后仍为0。

另以原 .mcp.json 的参数完成一次真实 context.deliverables 请求，返回已登记3项产物，再保留连接2秒观察。单个MCP服务主进程的峰值工作集约64.3 MiB、私有提交约48.9 MiB；启动器和控制台另计。请求上游格式器期间 Node 主进程峰值约62.3 MiB。测量客户端自身也使用 MCP SDK，不把它计作产品服务的常驻成本。没有实际加载或压测向量模型。

## 同负载前后对比

使用同一现有registry、原数据库、已确认的Codex会话和相同请求，直接回放适配器；不调用付费模型，不冒称新原生会话。每种负载前后各2次，进程树每20ms采样，包含Python启动器/实际进程及控制台；为短期本机观测，不是泛化基准或内存泄漏证明。

普通 PostToolUse 均值工作集下降约65%，峰值私有提交均值下降约81%；非文件 PreToolUse 类似。普通事件耗时0.421–0.438s降至0.297–0.344s，非文件事件0.547–0.563s降至0.297–0.328s。文件读取耗时波动较大，峰值无明显改善，不宣称其性能提高。多个并发会话仍会叠加开销。

## 改动与当前验证

native_assistance.marker 的 has 增加负向快速路径。宿主key固定为canonical JSON数组，使用固定上游 session-marker-files.ts 的同一文件名规则；只有确定无marker才返回false，存在/无法确定仍调用原TS。mark/take保持原代码。原R pending/prepared查询没有跳过，因此marker消费后尚未确认的交付仍能恢复。

file_history.literal_paths 对上游 extractFromMcp 本来就不支持的工具名直接返回空，不为非文件操作启动Node。原文件路径解析、实际查询、格式化和SQL gate保留。

新增 tests/test_hook_memory.py 两项当前行为用例：无pending时，故意不可用的可选Node不妨碍精确任务提交和普通工具后事件（先RED，后GREEN）；真实上游marker存在但Rail尚无pending审计时，仍返回精确恢复来源且重放不重复。最终2项通过，3.268s。随后同负载资源复测达到普通事件低于60 MiB目标。未运行旧套件、smoke、hash/措辞对比或启动/健康探针。

本聊天 outputs/profile-hook-memory.py、hook-memory-before.json、hook-memory-after.json、system-memory-observed.json、mcp-memory-observed.json 保留脱敏数据。已同步实际D:/ContextRail源码；原v1 entry每次Hook读取源码，不需要改Hook配置/信任或重启记忆服务。现有OpenSpec 5.4的Codex远程压缩及原main召回限制不因内存改进而视为解决。
